## 【续】「卡住不动了」诊断 —— 结论：没卡（假性卡死），并定型了一套日志取证流程

### 1) 先确认你看的是哪份日志（最大的坑）

- **真正实时的日志**：`%APPDATA%\SlayTheSpire2\logs\godot.log`；
  用户常把它复制到桌面再贴给我 ⇒ 桌面那份是**某一刻的快照**，之后游戏还在继续写。
- **判据**：比对桌面副本与实时日志的**行数/末行**。本次桌面副本 1,935,817 B / 15,731 行，
  末行 = 实时日志**第 15731 行**（`Player ready changed: 76561199054067370`）⇒ 精确等于 18:49:09 的快照，
  而实时日志 3 分钟后已 2.20 MB 并推进到战斗中。
- **Godot 启动时会轮转日志**：旧 `godot.log` 被改名成 `godot<YYYY-MM-DDTHH.mm.ss>.log`。
  所以「上一局的 desync 记录找不到了」通常只是轮转走了（本次轮转为 `godot2026-09-25T18.09.59.log`，
  且 `Get-Process .StartTime` = 18:09:59 与文件名吻合 ⇒ 可以据此定位"当前进程是哪次启动"）。

### 2) 判定「真卡死」三连（缺一不可）

```powershell
$p = Get-Process -Id <pid>            # ① 进程还在吗
$p.Responding                          # ② 主窗口消息泵还活着吗（False ⇒ 真卡死）
$c1=$p.TotalProcessorTime; Start-Sleep 6; $p.Refresh(); ($p.TotalProcessorTime-$c1).TotalMilliseconds  # ③ CPU 采样
```
再叠加 ④ **实时日志是否还在涨**（`stat -c%s` 两次采样）。本次 `Responding=True` + 6 秒 3391ms CPU +
日志持续增长 + 刚打赢一场战斗 ⇒ **不是卡死**。

### 3) 假性卡死：窗口失焦（本次的真凶）

- STS2 有 `MuteInBackground`：**窗口失焦即静音并降频**，画面看起来就像冻住。
- 查法：`grep "MuteInBackground" godot.log`，`FocusIn` 行里的 `msSinceFocusOut=` 就是失焦时长。
  本次在全会话最大的 38s 空档（18:48:37→18:49:15）里，失焦占了 **4.4s + 10.9s + 13.8s = 29s**，
  而用户 18:49:09 复制日志正好落在最后那段 13.8s 失焦期间 ⇒ 他看到的是失焦的窗口，不是卡住。

### 4) 用时间戳算停顿（日志用的是 UTC！）

`at HH:MM:SS` 是 **UTC**（本地 = UTC+8，`at 10:48:34` = 本地 18:48:34）。
用脚本把所有时间戳抽出来算相邻 gap，一次就能定位所有停顿。本次最大 38s，其余全是
`NetQualityTracker` 的 **20s 固定采样**（不是卡顿，别误判）。脚本：`.local/scan_gaps.py`。
同法确认「无慢操作」：全日志最大 `time_elapsed=884ms`（资源预载），开局载入约 5s，

### 正确修法（引擎侧已确认可行）

引擎的玩家选择**支持多索引**：`PlayerChoiceResult.FromIndexes(List<int>)` +
`RunManager.Instance.PlayerChoiceSynchronizer.SyncLocalChoice(player, choiceId, result)` 发送、
远端 `AsIndexes()` 重建（见 `CardSelectCmd.cs:359-433`）。
MinionLib 也给了同步右键的范式：`MinionLib.RightClick.Easy.EasyRightClickableModelHandler`

`ToNetAction()` 只序列化 `NetCombatCard`/`ModelId` 等可重建 id。

⚠️ 但**不能**简单套 `EasyRightClickCardAction`：右键发生在玩家选择窗口内，此时动作队列是
**paused** 的（`Pausing action … for player choice`），入队动作要等选择结束才执行 ⇒ 会晚于
`AfterFireComponentChoiceCompleted`，来不及。

⇒ 可行方案须把「右键点了哪张牌」**塞进玩家选择本身**（或加一轮同步选择），让两端用同一个索引重建

### 修法设计定稿（会话末尾补充，取代之前的 A/B 二选一）

复查同步原语后的结论 —— 两条硬约束：

1. `PendingRightClicks` 本身**两端一致**（`ModifyFireComponentRightClickQueue` 在两端用同 RNG 同步数据跑），
   分歧只出在「玩家点了哪张牌」这一步。
2. 右键发生在玩家选择窗口内，动作队列 paused ⇒ 把右键做成入队 `GameAction`（A/B 里的 B 案）**必然来不及**，
   会晚于 `AfterFireComponentChoiceCompleted`。A 案（改 `NChooseACardSelectionScreen` 多选）要动 UI 且
   `NChooseACardSelectionScreen` 只回单索引。

⇒ **采纳第三案（推荐）：把「应用」从 UI 阶段推迟到结算阶段，再加一轮同步选择。**

- UI 侧（`YalisalinFireComponentSelectionRegistry.TryHandleRightClick`）**只记录不应用**：
  把 `(CardIndex, KindIndex)` 追加进一个**纯 UI 临时缓冲**（不是 run state），跳过按钮记一个哨兵项。

- 结算侧（`YalisalinFireComponentResolver`，在 `context.ChosenCard = await ChooseCard(...)` 之后、
  `AfterFireComponentChoiceCompleted` 之前）插一轮**同步选择**：
  `RunManager.Instance.PlayerChoiceSynchronizer.ReserveChoiceId(player)` →

## 艾玛「魔女因子」无视强制限伤即死（EmaWitchFactorPower）

**需求**：`让艾玛的魔女因子在满足条件下时能无视像 hardened_shell 这样的强制限伤直接击杀敌人`。

### 根因

`EmaWitchFactorPower.AfterDamageReceived` 的即死结算原本走**伤害管线**：

```csharp
await CreatureCmd.Damage(choiceContext, Owner, Owner.CurrentHp,
    ValueProp.Unblockable | ValueProp.Unpowered, null, null);
```

而 `Hook.ModifyHpLost`（`Hook.cs:1725`）会在伤害管线内跑 4 个钩子，其中
`ModifyHpLostBeforeOstyLate` 就是 `HardenedShellPower` 的限伤入口
（`Math.Min(amount, Amount - damageReceivedThisTurn)`）⇒「血已到阈值却不死」。

**同一层级的限伤/减伤效果全在 `Hook.ModifyHpLost` 里**（grep `ModifyHpLost\w*\(` 一次性列全）：
`HardenedShellPower`(BeforeOstyLate) / `IntangiblePower`(AfterOsty) / `BufferPower`(AfterOstyLate) /
`SlipperyPower` / `TheBoot` / `TungstenRod` / `BeatingRemnant`，
以及本 mod 自己的 `ThirteenWaterIntelPower.ModifyHpLostBeforeOsty` / `AnanlinMargaretVoiceMagicPower.ModifyHpLostAfterOsty`。
**该钩子只在伤害管线里被调用** ⇒ 只要不走 `CreatureCmd.Damage`，就天生无视全部限伤。

### 用户拍板的取舍（重要）

先给了两个方案（`CreatureCmd.Kill(force:false)` vs `force:true`），用户**明确否决**：
> 「不要用 kill，还是保留原来的，只有遇到像 hardened_shell 这种的限伤才进行适配」

⇒ 最终形态 = **原伤害调用一字不改**，只在「伤害被削减」时补一手。

### 最终实现（`ManosabaLinCode/Characters/Ema/Powers/EmaWitchFactorPower.cs:57-68`）

```csharp
var results = await CreatureCmd.Damage(choiceContext, Owner, Owner.CurrentHp, ValueProp.Unblockable | ValueProp.Unpowered, null, null);
if (Owner.IsAlive && !results.Any(dealt => dealt.WasTargetKilled))
{
    await CreatureCmd.SetCurrentHp(Owner, 0);
}
```

* **判据为什么用 `DamageResult.WasTargetKilled`**：`LoseHpInternal` 里 `flag = CurrentHp > 0 && amount >= CurrentHp`，
  且文档明写「**即使随后被仙女瓶复活也仍为 true**」。于是它精确区分
  「伤害被削减（false ⇒ 补刀）」与「伤害打满但被防死（true ⇒ 不动）」，**不会越过防死效果**。
  换用 `Owner.IsAlive` 单独判断会把「仙女瓶复活」也误判成需要补刀。
* **补刀为什么用 `CreatureCmd.SetCurrentHp(Owner, 0)`**：`SetCurrentHpInternal` 直接写 `CurrentHp` 字段
  （`CurrentHp = Math.Min(amount, MaxHp)`），**不经过任何 `ModifyHpLost` 钩子**；随后 `if (creature.IsDead) await Kill(creature)`
  走引擎自己的死亡流程（`force` 默认 false ⇒ 防死效果照旧生效）。
  比 `Kill` 更贴合用户「不要用 kill」的措辞，效果等价 —— 注意**引擎自己的伤害管线末尾也是 `await Kill(killedCreatures)`**（`CreatureCmd.cs:430`），
  所以「用不用 Kill」在语义层级上其实是同一套死亡原语。
* `ValueProp` 没有「跳过限伤」的 flag（整个枚举只有 `Unblockable=2 / Unpowered=4 / Move=8 / SkipHurtAnim=0x10`），
  所以**不存在「换个属性就绕过限伤」的走法**。
* 反复调 `CreatureCmd.Damage` 也打不死：限伤上限是 `Amount - damageReceivedThisTurn`，
  第一击把 `damageReceivedThisTurn` 顶满后上限归 0，后续永远是 0 伤害 ⇒ **必须绕开管线**。

## 残骸首领（第一层 `GuardOneMonster`）战胜奖励：追加「升级两张牌」奖励条目

用户需求原话：「在击杀第一层替换的残骸BOSS后立刻让每个玩家选择两张牌组的卡进行升级，即战胜BOSS的奖励」。
`AskUserQuestion` 三点拍板：①呈现形式 = **奖励屏条目**（不是击杀瞬间弹窗）；②**先于**原有奖励（金币/药水/卡牌）；
③**仅第一层残骸**（不含第二层 `GuardTwoBoss`、第三层 `GuardThree`）。

### 关键调研结论（都是读源码得到的，别凭印象）

* **追加奖励的唯一公开 API**：`CombatRoom.AddExtraReward(Player, Reward)`（`CombatRoom.cs:185`，
  内部 `_extraRewards` 字典，会被 `ToSerializable`/`FromSerializable` 持久化）。
  奖励是**逐玩家**生成的 —— `CombatRoom.OfferRoomEndRewards()` 对 `CombatState.Players`
  每人调一次 `RewardsCmd.GenerateForRoomEnd(player, this)`，而 `RewardsSet.WithRewardsFromRoom`
  会把 `combatRoom.ExtraRewards[player]` append 进结果（`RewardsSet.cs:96`）。
  ⇒ **要「每个玩家都拿到」就必须对每个玩家各 Add 一条**，只加一条不够。
* **排序**：`RewardsSet.GenerateWithoutOffering` 末尾 `Rewards.Sort((x,y)=>x.RewardsSetIndex.CompareTo(y.RewardsSetIndex))`
  （`List.Sort` 不稳定，但 0 是唯一最小值所以确定排最前）。
  原版取值：Gold=1 / Potion=2 / Relic=3 / SpecialCard=4 / Card=5 / CardRemoval=7。
  ⇒ **自定义奖励用 `RewardsSetIndex => 0` 即排在最前**。
* **RitsuLib 已经内置自定义 reward 框架**（0.6.2 的 `STS2-RitsuLib.Runtime.dll` 里有：
  `ModCustomReward` / `ModRewardRegistry` / `ModRewardDefinition` / `ModRewardSerialization` /
  `IModSerializableReward`；`STS2-RitsuLib.dll`（loader）里也有同名行）：
  * `ModCustomReward : Reward, IModSerializableReward`：封装了 `Description`（默认表
    `gameplay_ui`、默认 key = 注册 id）、`RewardIconPath`、`CreateIcon()`、`Populate()`、
    `ToSerializable()`；基类 `RewardsSetIndex => 9`（**必须自己覆盖成 0**）。
  * 注册：`ModRewardRegistry.For(ModId).RegisterOwned(stem, (save, player, json) => new …(player))`
    ⇒ id = `GetCompoundId(ModId, "REWARD", stem)` = **`MANOSABA_LIN_REWARD_<NORMALIZE(stem)>`**，
    同时 `DynamicEnumValueRegistry<RewardType>` 按 `reward:<id>` 哈希**确定性铸造一个动态 RewardType**
    ⇒ 联机双方算出的值一致，读档/同步都稳。
  * 读档重建由 RitsuLib 的 Harmony 前缀 `RewardFromSerializableExtPatch` 接管
    （`ModRewardRegistry.TryCreate(save.RewardType, …)`），sideband JSON 存在
    `SerializableRoom.EncounterState["__mod_reward_ext_<netId>_<index>"]`。
    ⇒ **注册必须发生在任何奖励被构造/反序列化之前** ⇒ 放在 `MainFile.Initialize()`。
* **副作用（选卡+升级）的联机做法**：奖励集合「选了哪一条」由原版 `RewardsSetSynchronizer`
  按 rewardIndex 同步，但 `OnSelect()` 会在**每台机器**上跑。所以副作用必须确定性：
  用 `CardSelectCmd.FromDeckForUpgrade(player, prefs)`（内部 `PlayerChoiceSynchronizer.ReserveChoiceId`
  + `SyncLocalChoice`）—— 与 vanilla `CardRemovalReward` → `RewardSynchronizer.DoUnsyncedCardRemoval`
  完全同构。**不要自己弹 UI、不要用本地随机**。
* **`NDeckUpgradeSelectScreen` 的一个坑**：`CheckIfSelectionComplete` 要求
  `_selectedCards.Count >= prefs.MaxSelect`，`_closeButton` 只在 `prefs.Cancelable` 时才 Enable。
  ⇒ 如果写死 `MaxSelect = 2` 而牌组只有 1 张可升级牌，**确认按钮永远点不了 ⇒ 卡死选卡界面**。
  正确做法：先数 `PileType.Deck.GetPile(Player).Cards.Count(c => c.IsUpgradable)`，
  `selectCount = Math.Min(2, upgradableCount)`；`upgradableCount == 0` 时直接 `return true`
  （算作已领取，避免奖励卡在奖励屏上）。
* **触发点选 `GuardOneMonster.AfterDeath`**：该文件本来就在这里设置二/三层 BOSS，是「击杀残骸后」的
  既有钩子。注意 `CreatureCmd.KillWithoutCheckingWinCondition` 会**先**用
  `wasRemovalPrevented: true` 调一次 `Hook.AfterDeath`（死亡被阻止），之后真死时再用 `false` 调一次
  ⇒ 必须 `if (!wasRemovalPrevented && !_bossRewardGranted)`。`AfterDeath` 时
  `RunManager.Instance.State.CurrentRoom` 仍是那个 `CombatRoom`（战斗要到 `EndCombatInternal` 才结束，
  且 `Hook.AfterDeath` 早于 `CombatManager.RemoveCreature`）⇒ 此时 `AddExtraReward` 会被后续
  `OfferRoomEndRewards` 读到，时序正确。
* 为什么不用 `PowerModel.AfterCombatEnd(CombatRoom room)`（`ForbiddenGrimoirePower` / `RoyaltiesPower`
  那种范式）：`Hook.AfterCombatEnd` 遍历 `runState.IterateHookListeners(combatState)`，而
  `CombatState.IterateHookListeners()` 只遍历**当前还在 `_allies`/`_enemies` 里的生物**；
  BOSS 死亡后会被 `RemoveCreature` 移除 ⇒ 它的 power / `MonsterModel` 钩子**拿不到**。
* **文案表用 `gameplay_ui`**（原版战斗奖励条目都在这张表：`COMBAT_REWARD_CARD_REMOVAL` 等），
  不是 `cards`/`relics`。引擎侧加载规则（已核实）：`LocManager.LoadTablesFromPath` 只按

```
  at EmaWitchFactorPower.AfterDamageReceived(...)        ← 即死的嵌套伤害
```

* `CreatureCmd.KillWithoutCheckingWinCondition`（`CreatureCmd.cs:590-602`）的**防死分支顺序 = 先
  `Hook.AfterDeath(wasRemovalPrevented: true)`，再 `Hook.AfterPreventingDeath(preventer, creature)`**。
* `GuardTwoBossMonster.AfterDeath` **没判 `wasRemovalPrevented`** ⇒ 诈尸那一刻就去
  `RewardsCmd.OfferCustom(player, [CardReward(...)])` 发卡牌奖励 —— 而 `OfferCustom` 的注释写着
  「Offers a custom set of rewards…The rewards screen generated by this cmd will disappear…」，
  是一个**完整的奖励屏 + 选牌（`CardSelectCmd`）流程**，此刻正嵌在伤害管线里
  （`HookPlayerChoiceContext.AssignTaskAndWaitForPauseOrCompletion`）。
* 于是这条奖励流程抛异常 / 走选择，把紧接着的 `AfterPreventingDeath`
  （`SetMaxAndCurrentHp(999999999)` + `HpDisplay.InfiniteWithoutNumbers` + `GainBlock`）**整段吃掉**
  ⇒ BOSS 停在 0 血，诈尸音效（`PlayLastStandMusic`）已经放了，却没有复活也没有盾。
* **为什么只在魔女因子下暴露**：即死是**嵌套伤害**——必然经过「非致命外层伤害 → `AfterDamageReceived` →
  再打一次等于当前生命的伤害」，而这时 BOSS 通常还没打出 `ATTACK_3`（即 `WithPower` 尚不存在），
  于是「诈尸护盾 = `WithPower × 3` = 0」这个第二重问题同时成立。

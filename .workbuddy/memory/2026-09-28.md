### 本轮实测出来的 RitsuLib `[ModInterop]` 硬规则（**读源码得来，不是照抄文档**）

源码：`.local/external/STS2-RitsuLib/src/Interop/Internal/ModInteropEmitter.cs`

- **目标 mod 未加载 ⇒ `assemblies.Count == 0 ⇒ return`**（`:41`）⇒ **保留你写的默认方法体**。
  这就是「`IsReady => false`」这套门面成立的机制，也正是「缺失当正常分支」的实现方式。
- 外层 interop 类成员必须 **public + static**（`requireStatic: true`，`:47`/`:76`），否则该成员被**跳过**。
- **返回类型必须与远端完全相等**（`:210` 用 `!=` 比较，不做协变）⇒ 不匹配抛异常 → 被 catch 成
  **`Warn` + 静默降级**。⚠️ **这是最大的运维风险：签名写错不会崩，只会安静不生效。**
- 嵌套 `InteropClassWrapper` 包装类必须有 public 构造，且**远端要有参数完全匹配的构造**（`:102`/`:113`），
  否则整类 Warn + 跳过后续成员。
- ⇒ **必须加启动自检**：看 RitsuLib 日志有没有 `[ModInterop] Generated interop method/type …`；
  只有 `Warn` 没有 `Generated` = 代理没挂上，而 `IsReady` 此时会骗人。
- `[InteropTarget]` 有 (type,name) 与 (name) 两个重载；`[InteropAnyParam]` 显式声明通配参数。
- 类型名含逗号 → 走 `[AssemblyInterop]`；不含 → 走 `[ModInterop]`（`IsAssemblyQualified` 判定）。
- 前置条件**已满足**：`MainFile.cs:60` 已有 `ModTypeDiscoveryHub.RegisterModAssembly(ModId, assembly)`。

### 其它已核实的事实

- `MainFile.cs:100` 是**无条件** `harmony.PatchAll()` ⇒ 跨 mod patch 必须自己条件化。
  推荐 `[HarmonyPrepare] static bool Prepare() => XxxCompat.IsLoaded();`（`0Harmony.dll` 元数据里确认
  `HarmonyPrepare` / `Cleanup` / `CreateClassProcessor` 都在）。备选：把 `PatchAll` 拆成

- 反射解析目标方法的先例：`ManosabaLinCode/Patches/SamePlaceTruthSelectionLockPatch.cs:49` 的 `TargetMethod()`
  （直写 `[HarmonyPatch(typeof(...))]` 就等于硬引用，不能用于可选依赖）。

  ⇒ 无法反编译它的扩展点，方案里把「它有没有公开注册 API」列为待确认输入。
- `CompatContentGate` 注释里被注掉的 `WindchaserCompat.IsLoaded()`（`VariantPersonWindchaserThePlaneswalker` /
  `SkillGrantSpark`）说明**这套门控当初就是为跨 mod 联动设计的**，只是没接线。

## 16:50 跨平台取证：否决「需为 macOS 重编译 DLL」（**纯取证，未改任何源码/配置**）

群友转来外部判断（称 `ManosabaLin.dll` 是 Windows x86-64 程序集、依赖 `Vortice.DirectX`/`DXGI`/

   ⇒ **误打包合计只有 0.64 MiB（0.1%）；614 MB 的主体是纹理，砍不掉。**

### ⚠️ 两个误判陷阱（对方和我都踩了）

### 顺带挖到的硬约束（写进施工单 §0）

## 20:45 用户裁定遗物 5：「有正义就能生效，多余的正常保存为伪证」—— 6 条偏差全部闭环

用户原话：「遗物 5 是有正义的时候消耗一层正义当 4 层伪证用，**也能生效**，要是多余的就**正常保存为伪证**。」

**旧实现的限制**：`TryConsumePerjuryForDeficit` 第一句就是 `if (perjury is null) return false;`
⇒ 玩家**一层【伪证】都没有**时，即使有【正义】也用不出这个遗物。原因是「同步扣费前缀里没法新建 Power
（`PowerCmd.Apply` 是 async）」。

**解法：改用「同步建 Power」这条路**
```csharp
var created = ModelDb.Power<PerjuryPower>().ToMutable();   // canonical → 可变副本
created.ApplyInternal(Owner.Creature, remaining, silent: true);
```
- `PowerModel.ApplyInternal(owner, amount, silent)`（`PowerModel.cs:564`）= `Owner = owner` → `SetAmount(...)` → `Owner.ApplyPowerInternal(this)`；
  **最后一步才是注册监听器**，等于 `PowerCmd.Apply` 的同步内核（`PowerCmd.cs:139` 也是这么调的）。
- `ToMutable(int initialAmount = 0)`（`:555`）= `MutableClone()` + 记 `CanonicalInstance` + 设 Amount。
- ✅ **多余层数天然留存**：`ApplyInternal` 与 `SetAmount` 都**不触发** `AfterApplied` / `AfterPowerAmountChanged`
  ⇒ 兑换出的剩余【伪证】**不会**被 `PerjuryPower.CheckAndConvert`「满 5 转【正义】」吃掉，原样留成【伪证】。
  这正好是用户要的「多余的就正常保存为伪证」。（与既有 `PerjuryPower.ConsumeForGuard` 同一套做法。）
- `CanCoverEnergyDeficit` **早就**把【正义】折算进来了（`available += justice × 4`），所以 `HasEnoughResourcesFor`
  那侧一直是对的 —— 之前单纯是**消费侧**走到 `perjury is null` 就返回 false。⇒ 只改了消费侧，UI 侧没动。
- 顺带把 `CanCoverEnergyDeficit` 的写法收紧成 `perjury?.Amount ?? 0`（不再对 null 提前 `return false`）。

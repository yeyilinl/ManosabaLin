## 16:55 四合一 issue 取证 + 火色 v2 按当前本地化对齐（用户：余火三缺陷+残骸BOSS意图汇总成一个 issue）

### 起因

用户要求把 4 件事**汇总成一个 issue**：① 余火打出的手牌**卡模型**；② 余火选牌**选零费也扣费**；
③「把道歉烧成灰」自动打出**应当免费**；④ 残骸 BOSS 一阶段上毒意图改为**判定**（有 ⇒ 1 层虚弱，无 ⇒ 照常上毒）。

### 取证结论（实读代码，未改一行）

**① 卡模型 = 双重入堆（高置信）**
`YalisalinFireComponentResolver.PlayCardWithSuppressedFireComponent` 先调
`MoveCardToPlayPileForFireComponent`（`CardPileCmd.Add(card, PileType.Play, skipVisuals: true)`），
**紧接着** `card.OnPlayWrapper(..., isAutoPlay: true, skipCardPileVisuals: true)` —— 而引擎的
`CardModel.OnPlayWrapper`（`.local/.../CardModel.cs:1875+`）在 `isAutoPlay` 分支里**自己又会**
`CardPileCmd.Add(this, PileType.Play, ..., skipCardPileVisuals)` ⇒ 同一张牌入堆两次、视觉跳过两次 ⇒ 手牌区留孤儿节点。
⇒ 修法：删掉手动入堆，交给引擎（对照 `PlayCardAction.ExecuteAction`：先 `SpendResources` 再 `OnPlayWrapper(isAutoPlay:false)`）。

**② 扣费 = 费用「两套账」**
- 预览账 `YalisalinFireComponentContext.GetEffectiveCost`（含 `GetPendingTemporaryCostOffset`）**只用于 CanPlay 判定**；
- 真实账 `CardModel.SpendResources()` → `EnergyCost.GetAmountToSpend()` = `max(0, GetWithModifiers(All))`，**不含 context 偏移**；
- context 偏移要落到真实账**必须**显式 `ApplyTemporaryCostOffset(card)`，而它有
  `_appliedTemporaryCostOffsets.Add(card)` **去重** ⇒ 同一张牌第二次进余火**不再落偏移**（候选根因 B）；
- `AfterFireComponentChoiceCompleted` 里的 `AddTemporaryCostOffset(context.ChosenCard, -1)` **在选牌完成后才登记** ⇒ 只影响预览（候选根因 C）；
- `SetThisTurnOrUntilPlayed` 用的是 `WhenPlayed` 到期，引擎在 `OnPlayWrapper` **结尾** 才 `EnergyCost.AfterCardPlayedCleanup()`（`CardModel.cs:2007`）⇒ 正常路径下 0 费有效，余火路径因先手动入堆可能提前失效（候选根因 A）。
⇒ 建议：**取消两套账**，把"免费/减 N"直接落成真实 `EnergyCost` 修改，`GetEffectiveCost` 退化为读 `EnergyCost`。

**③ 道歉烧成灰确实在扣费**
`BurnedApologyPower` 只是个 `IsVisibleInternal => false` 的**开关**；真实触发在
`YalisalinsHairpin.BeforeFireComponentBurned`（第 693 行）设 `CustomData["AutoPlayBurnedCard"] = true`；
之后走的是与 ①② **完全相同**的路径，`PlayCardWithSuppressedFireComponent` 里 `card.SpendResources()` **真实扣费**，没有任何置 0 处理。
⇒ 修法：给该路径加 `free` 开关，免费时**不调** `SpendResources`（直接给 `ResourceInfo{0,0,0,0}`）；
⚠️ X 费牌必须给 `CapturedXValue` 一个确定值（否则 `CostsX` 会按玩家全部能量结算）。
文案 `MANOSABA_LIN_CARD_BURNEDAPOLOGY.description` 现在**没说免费也没说扣费** ⇒ 修完要补一句「不消耗能量」（5 语言同步）。

**④ 残骸 BOSS 改判定**
`GuardOneMonster.cs:65` `POISON_MOVE = new MoveState("POISON_MOVE", PoisonMove, new DebuffIntent())`；
`PoisonMove`（第 117 行）对每个 target `PowerCmd.Apply<PoisonPower>(6)` + 自己 `WithPower(30/50)`。
改法：逐目标 `target.GetPower<PoisonPower>() is { Amount: > 0 }` ⇒ 有则 `Apply<WeakPower>(1)`，无则照常上毒。
✅ **虚弱 = `WeakPower`**（`MegaCrit.Sts2.Core.Models.Powers/WeakPower.cs`，Debuff/Counter，本文件已 using）。

## 17:03 用户纠正：火色消耗方向是「从最新格」；21 张定稿卡面入 issue

### ⚠️ 上一轮我把方向搞反了（重要教训）

我上一轮据用户「从第一格开始消耗」把设计文档改成 **FIFO**，并据此判定「本地化 `…fireColor.description` 写『消耗最新火色』是文案错误」。
**两句都是错的。** 用户本轮原话：「当亚里沙攻击后就**从最新格开始消耗**火色并触发额外效果」⇒ **代码方向才是要改的那一边**。

**记住这条推论（以后不用再纠结）**：
> **格位定色 ⟺ 从最新/最高格消耗。**
> 填格 1→6、消耗 6→1 ⇒ 量表恒为 `{1..n}` 连续前缀，**永远没有空洞**。
> 若改成从第 1 格（最早格）消耗：消耗后留前洞，下次给予补到第 1 格（新火色插队）；若左对齐压缩，第 3 格的亮黄会移到第 2 格（定义是浅橙）⇒ 与格位定色直接冲突。
> ⇒ 「压缩与否」不是待裁定项，而是**由方向直接决定的推论**。

**另：现场代码方向确实是反的** —— `YalisalinFireColorGauge.Consume`（`YalisalinsHairpin.cs:1483`）取 `ordered[0]`，`Order = ++conversionSequence` ⇒ 消耗**最早**一格。**要改代码，不是改文案。**

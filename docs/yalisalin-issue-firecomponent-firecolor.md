## 一、余火组件 3 个缺陷（A 类）

### 1.1 A1：余火打出的手牌「卡模型」

#### 复现路径

1. 打出一张带【余火】组件的牌 → 进入余火选牌界面；
2. 选一张**手牌**作为「打出」的那张；
3. 该牌被自动打出 → **卡面模型卡在原地**（视觉残留 / 不消失 / 位置错乱）。

#### 代码证据链

`YalisalinFireComponentResolver.cs`

```csharp
// 155 行
await PlayChosenCardIfPossible(choiceContext, context, context.ChosenCard);

// 389 行
private static async Task PlayCardWithSuppressedFireComponent(...)
{
    context.ApplyTemporaryCostOffset(card);
    ...
    await MoveCardToPlayPileForFireComponent(card);      // ← ① 手动入 Play 堆
    ...
    var (energySpent, starsSpent) = await card.SpendResources();
    ...
    await card.OnPlayWrapper(choiceContext, target, isAutoPlay: true, resources, skipCardPileVisuals: true);
}

// 430 行
private static async Task MoveCardToPlayPileForFireComponent(CardModel card)
{
    if (card.Pile?.Type == PileType.Play) return;
    await CardPileCmd.Add(card, PileType.Play, skipVisuals: true);   // ← ① 入堆但「跳过视觉」
}
```

而**引擎自己在 `OnPlayWrapper` 里已经会入堆**（`.local/probe_engine/decomp/MegaCrit.Sts2.Core.Models/CardModel.cs:1875+`）：

```csharp
if (!isAutoPlay)
{
    await CardPileCmd.AddDuringManualCardPlay(this);
}
else
{
    await CardPileCmd.Add(this, PileType.Play, CardPilePosition.Bottom, null, skipCardPileVisuals);  // ← ② 又入堆一次
    if (!skipCardPileVisuals)
        await Cmd.CustomScaledWait(0.25f, 0.35f);
}
```

#### 疑似根因（高置信）

**同一张牌被入 Play 堆两次**：先在 `MoveCardToPlayPileForFireComponent` 里以 `skipVisuals: true` 塞进去（此时**卡的 UI 节点没有被搬运**），随后 `OnPlayWrapper(isAutoPlay: true)` **又**执行一次 `CardPileCmd.Add(..., skipCardPileVisuals: true)`。视觉被跳过两次 ⇒ 手牌区的节点成了"孤儿"：模型留在原地、逻辑上已经不在手牌。

对比：**正常打出**走 `PlayCardAction.ExecuteAction` → `OnPlayWrapper(isAutoPlay: false, ...)` → 引擎用 `AddDuringManualCardPlay` 统一处理搬运 + 动画，**不需要调用方手动入堆**。

#### 建议修法（择一）

- **A（推荐）**：删掉 `MoveCardToPlayPileForFireComponent` 的调用，只保留 `await card.SpendResources()` + `card.OnPlayWrapper(isAutoPlay: true, ..., skipCardPileVisuals: false)`，让引擎照常做搬运与动画。
  - ⚠️ 前提：`SpendResources()` 之前必须先保证牌**还在手牌**（引擎的 `PlayCardAction` 也是先扣费再入堆）。当前 `CanPlayFromFireComponent` 依赖 `card.Pile` 状态，删入堆后要复核一遍判定时机。
- **B**：保留手动入堆，但改成 `skipVisuals: false`（走正常搬运），并且**不再**让 `OnPlayWrapper` 走 autoPlay 分支（改为 `isAutoPlay: false` + `CardPileCmd.AddDuringManualCardPlay` 路径）。
- 另外统一 `Burn` 的视觉参数：`context.SkipBurnVisuals` 目前默认值需要确认（`YalisalinFireComponentContext.cs:101` 是个可写属性），入堆跳视觉而烧牌不跳视觉，本身也容易出"半张牌"的残留。

#### 待确认

- `SkipBurnVisuals` 在哪几处被设成 true？
- 现象是**只在多人**出现，还是单人也能复现？（多人下 `CardPileCmd` 的本地表现 / 同步差异会导致不同症状）

### 1.2 A2：余火选牌「选零费牌也扣费」

#### 关键机制事实（已实读，非猜测）

余火这条路径上**存在两套互不相通的「费用」账**：

| 账       | 谁在用                                                            | 计算式                                                                                           | 用途             |
| ------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | -------------- |
| **预览账** | `YalisalinFireComponentContext.GetEffectiveCost`               | `max(0, EnergyCost.GetWithModifiers(All) + GetPendingTemporaryCostOffset(card) + additional)` | **只判断"能不能打出"** |
| **真实账** | `CardModel.SpendResources()` → `EnergyCost.GetAmountToSpend()` | `max(0, EnergyCost.GetWithModifiers(All))` —— **不含** `context` 里的任何待应用偏移                      | **真正扣钱**       |


而 `context` 侧的偏移要落到真实账上，**必须显式调 `ApplyTemporaryCostOffset(card)`**（`YalisalinFireComponentContext.cs:305`）：

```csharp
public void ApplyTemporaryCostOffset(CardModel card)
{
    if (!_appliedTemporaryCostOffsets.Add(card)) return;   // ← 去重：同一张牌只落一次
    var offset = GetTemporaryCostOffset(card) - _immediatelyAppliedCostOffsets.GetValueOrDefault(card);
    if (offset != 0) card.EnergyCost.AddThisTurnOrUntilPlayed(offset);
}
```

#### 三个候选根因（按可能性排序）

**根因 A｜「额外连接的那张随机牌」的 0 费只写进了预览账，且可能提前失效**

`YalisalinsHairpin.ModifyFireComponentChoiceOptions`（第 636 行）：

```csharp
generated.EnergyCost.SetThisTurnOrUntilPlayed(0, reduceOnly: true);  // ← 真实账：设 0（WhenPlayed 到期）
context.AddTemporaryCostOffset(generated, -999);                     // ← 预览账：再 -999
```

`SetThisTurnOrUntilPlayed(0, reduceOnly: true)` 用的是 `LocalCostModifierExpiration.EndOfTurn | WhenPlayed`，而引擎的清理时机是 `OnPlayWrapper` **结尾** 的 `EnergyCost.AfterCardPlayedCleanup()`（`CardModel.cs:2007`）。  
⇒ 在**正常路径**下扣费发生在清理之前，0 费有效。  
⇒ 但余火路径**先手动入 Play 堆**（见 A1）再扣费，若入堆/搬运过程触发了 `WhenPlayed` 清理，**0 费会在扣费前失效** ⇒ 症状正好是"选了显示 0 费的牌仍扣费"。  
**验证方法**：在 `SpendResources()` 前打印 `card.EnergyCost.GetAmountToSpend()`，看是不是等于原始费用。

**根因 B｜`ApplyTemporaryCostOffset` 的去重，让同一张牌第二次进余火时不再免费**

`_appliedTemporaryCostOffsets` 是 `HashSet<CardModel>` 且**按 instance 判等**。同一张手牌在一场战斗里被余火选中第二次时：

- 第一次：`Add` 成功 → 真实账落 -999/-1；
- 第二次：`Add` 失败 → **直接 return**，真实账不再落任何偏移。  
  ⇒ 第二次就变成"预览 0 费 / 真实原价"。

**根因 C｜`-1` 偏移登记太晚，只影响预览**

`AfterFireComponentChoiceCompleted`（第 668 行）里：

```csharp
context.AddTemporaryCostOffset(context.ChosenCard, -1);   // ← 选牌已完成之后才登记
```

而 `PlayChosenCardIfPossible` 在选牌**流程内**就已经把牌打出去了 ⇒ 这个 -1 只会体现在 UI 上，永远不会进真实账。

#### 建议修法

**根本解法：取消"两套账"**。把"这次打出免费 / 减 N 费"一次性落成**真实费用修改**（`SetThisTurnOrUntilPlayed(0)` 或 `AddThisTurnOrUntilPlayed(-N)`），扣费完全交给 `EnergyCost`；`GetEffectiveCost` 退化为**纯读取**（`EnergyCost.GetAmountToSpend()`），不再叠加 `context` 偏移。  
附带收益：`GetPendingTemporaryCostOffset` / `_immediatelyAppliedCostOffsets` / `_appliedTemporaryCostOffsets` 三套记账可以一起删掉，`CanPlay` 判定与真实扣费天然一致。

若想先最小改动止血：至少让 `ApplyTemporaryCostOffset` **不要用去重集合**（或改成"每次触发都保证真实账等于预览账"的幂等对齐），并修掉根因 C 的登记时机。

### 1.3 A3：「把道歉烧成灰」自动打出**应当免费**，现在真的在扣费

#### 现状（确实在扣费）

`BurnedApologyPower.cs` **只是个开关**，没有任何费用处理：

```csharp
/// 存在即生效（层数无意义，仅作为开关）。
public sealed class BurnedApologyPower : ManosabaPowerTemplate
{
    protected override bool IsVisibleInternal => false;   // 状态栏不显示
}
```

真实触发点在 `YalisalinsHairpin.BeforeFireComponentBurned`（第 693 行）：

```csharp
if (Owner.Creature.GetPower<BurnedApologyPower>() != null)
    context.CustomData["AutoPlayBurnedCard"] = true;
```

然后走的是**和 A1、A2 完全同一条**路径：

```
TryAutoPlayBurnedCard (Resolver:288)
  → CanPlayFromFireComponent(...)          // 用「预览账」判能不能打
  → PlayCardWithSuppressedFireComponent
      → MoveCardToPlayPileForFireComponent
      → await card.SpendResources()        // ← 在这里真的扣钱
      → OnPlayWrapper(isAutoPlay: true, ...)
```

**没有任何地方给它置 0 费**（`ModifyFireComponentChoiceOptions` 只处理"额外连接的随机牌"，管不到被烧牌）。  
⇒ 自动打出一张 2 费牌，就实扣 2 费 —— 与预期（免费）不符。

#### 文案现状 vs 预期

| 键                                                              | 内容                                        |
| -------------------------------------------------------------- | ----------------------------------------- |
| `MANOSABA_LIN_CARD_BURNEDAPOLOGY.title`                        | 把道歉烧成灰                                    |
| `MANOSABA_LIN_CARD_BURNEDAPOLOGY.description`                  | 被余火烧掉的牌若可以打出，先自动打出1次，然后再烧掉。\n自动打出的牌不触发余火。 |
| `ManosabaLin.YalisalinFireComponent.enhancement.burnedApology` | 烧掉的牌自动打出1次，然后再烧掉。                         |

⇒ 文案**没说免费**，也**没说扣费**；用户裁定 **应当免费** ⇒ **文案需要补一句"不消耗能量"**（5 语言同步）。

#### 建议修法

在 `PlayCardWithSuppressedFireComponent` 上**加一个 `bool free` 参数**（或让 `TryAutoPlayBurnedCard` 走专用分支），免费路径下：

- **不要**调 `card.SpendResources()`，直接构造 `new ResourceInfo { EnergySpent = 0, EnergyValue = 0, StarsSpent = 0, StarValue = 0 }` 传给 `OnPlayWrapper`；
- ⚠️ **不要**靠 `SetThisTurnOrUntilPlayed(0)` 绕过——即使扣到 0，`IsCanPlay` / `Hook` 侧仍可能有别的账（见 A2 根因 A），而且会污染这张牌本次的费用显示；
- ⚠️ X 费牌：`SpendResources` 对 `CostsX` 会 `CapturedXValue = amount`（= 玩家全部能量）。免费路径**必须**给 `CapturedXValue` 一个确定的 X（建议 0），否则自动打出会按当前能量全额结算、甚至抽干能量。

### 1.4 A1+A2+A3 共同修法（强烈建议合并）

| 步骤 | 内容                                                                             |
| -- | ------------------------------------------------------------------------------ |
| 1  | 删掉手动 `MoveCardToPlayPileForFireComponent`，入堆统一交给 `OnPlayWrapper`               |
| 2  | 给 `PlayCardWithSuppressedFireComponent` 加 `free` 开关；免费时**不调** `SpendResources` |
| 3  | 把 `context` 的费用偏移改成"直接改真实费用"，`GetEffectiveCost` 退化为读 `EnergyCost`              |
| 4  | 统一 `skipCardPileVisuals` / `SkipBurnVisuals` 的取值，避免半张牌残留                       |

### 3.1 六格量表 + 格位定色

| 格位 | 1  | 2  | 3  | 4  | 5  | 6  |
| -- | -- | -- | -- | -- | -- | -- |
| 颜色 | 浅橙 | 浅橙 | 亮黄 | 亮黄 | 赤红 | 赤红 |

- 载体**不用改**：`Dictionary<Creature, YalisalinFireColorGauge>` + `MaxSegments = 6`（`YalisalinsHairpin.cs:17`）。
- 颜色**由格位决定**，不是由"段"自带 ⇒ 这直接判了「**封存**」（把一段火色抽出量表、再插回指定位置）死刑：  
  插回第 3 格该算浅橙还是亮黄？没有自洽答案 ⇒ **封存整套删掉**（见 §3.8）。

### 3.2 给予：由**卡牌效果**给，从低格往高格填

- 填格顺序：1 → 2 → 3 → 4 → 5 → 6（找最低的空格）。
- **攻击不再自动给火色** ⇒ 删掉发夹描述里的「你用卡牌对敌人造成伤害后，给予其 1 段浅橙火色」。  
  （这条正是"攻击既给火色又引爆火色"的糊涂账来源，拆开之后两条线才各自干净。）
- ⚠️ **副作用（未裁）**：基础牌 `YalisalinAttack` / `YalisalinDefend` 的卡面在定稿表里**没变** ⇒ **起手没有任何途径给火色**（见 §七 第 5 项）。

### 3.3 消耗：从**最新格**开始

#### 规则

- 从**当前已填的最高格**开始消耗，依次往低格烧（后进先出）。
- 因为"填格从低往高"，**最高格 = 最新给予的那一格** ⇒ "从最新格"与"从最高格"是同一件事。
- 满 6 格时消耗顺序：`6 赤红 → 5 赤红 → 4 亮黄 → 3 亮黄 → 2 浅橙 → 1 浅橙`。

#### ⚠️ 现状代码方向是反的 ⇒ **要改的是代码，不是文案**

| 位置                                                             | 内容                                                                     | 结论                                                         |
| -------------------------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------- |
| `…HAIRPIN.fireColor.description`                               | 文案：「造成伤害会消耗**最新**火色」                                                   | ✅ **文案是对的**（与定稿一致）                                         |
| `YalisalinFireColorGauge.Consume`（`YalisalinsHairpin.cs:1483`） | 代码：取 `ordered[0]`，而 `Order = ++conversionSequence` ⇒ 实际消耗**最早（最旧）那一格** | ❌ **代码方向必须改**（改为消耗已填的最高格）                                  |
| `…HAIRPIN.description`                                         | 「你用卡牌对敌人造成伤害后，消耗其**1段浅橙火色**」                                           | ⚠️ 表述不严谨：消耗的是"最高格"，标签颜色随填格数变化（满格时是赤红）⇒ 建议改成「消耗其 **1 格**火色」 |

#### 💡 为什么「格位定色」必须配「从最高格消耗」

填格 1→6、消耗 6→1 ⇒ 量表恒为 `{1..n}` 的**连续前缀**，**永远不会出现空洞**。

反之，若从第 1 格（最早格）消耗：

- 消耗掉第 1 格后留**前洞**，下次**给予**会补到第 1 格 ⇒ 新火色"插队"，比 2~6 格的老火色先被消耗；
- 若改成"左对齐压缩"，第 3 格的亮黄会移到第 2 格（定义是**浅橙**）⇒ 与格位定色直接冲突。

⇒ **格位定色 ⟺ 从最新/最高格消耗**，两者是绑定的。"要不要压缩"因此**不是待裁项**，而是方向决定的推论。

#### 口径修订史（避免再次反复）

| 轮次            | 说法                                | 状态                        |
| ------------- | --------------------------------- | ------------------------- |
| 更早一轮          | 「攻击后**从最新格**开始消耗，即当前有五格就从第五格开始消耗」 | ✅ 与定稿一致                   |
| 中间一轮          | 「亚里沙攻击后就**从第一格**开始消耗火色」           | ❌ **作废**（与格位定色冲突，会在量表里留洞） |
| **定稿（17:03）** | 「亚里沙攻击后就**从最新格开始消耗**火色并触发额外效果」    | ✅ **以此为准**                |

### 3.4 连续：**同色**才算连续

> 第一次消耗火色之后，**第二次消耗若和第一次颜色相同**就是连续。

链条规则：每引爆一格，与**上一次**引爆的颜色比较；同色 ⇒ 链 +1，触发该色的「连续第 2 段」奖励；异色 ⇒ 链重置为 1。

- ✅ 定稿原话「**连续消耗两段同色有额外收益**」⇒ 采用**同色**。
- ❌ 旧稿那句「多段连续消耗**不同**火色触发额外效果」**作废**（`Unusedconclusion`/`Samewrongproblem`/`BoundPrometheus` 三张的"不同色"在定稿表里已全部改掉）。
- 同色连锁之外是否另设「贯穿奖励」（一次烧穿 ≥2 种颜色额外 +1 能量/抽 1 张）⇒ **默认不做**。

#### 现行三色文案（原文，`zhs/relics.json`）

⇒ 在"从最新格消耗"规则下，「最高火色」= 第 5/6 格的赤红 ⇒ 作用是**保住赤红、往里烧亮黄/浅橙**，

**黑红碳化**（`…fireColor.blackRed.description`，原文）：

> 魔女化后的特殊火色。当前由魔女化和黑红专属效果兑现。

⇒ 六格里没有它的位置 ⇒ **删**，但要连带清账（见 §3.8）。

#### 要删掉的

- 三色的「**回合开始时**」效果（浅橙抽牌 / 亮黄能量 / 赤红力量+敏捷）。  
  理由：改后的火色只有**给予 / 引爆 / 连续**三条线，回合开始自动产出是第四条，而且是"躺着拿"——  
  会让"填满 6 格"这件事失去意义，也和"火色由卡牌给予"自相矛盾。
- **黑红碳化**（第四种颜色）。

### 3.6 烧穿满格的节奏（满格连打 6 次攻击）

| # | 烧掉格 | 颜色 | 链     | 结果                        |
| - | --- | -- | ----- | ------------------------- |
| 1 | 6   | 赤红 | 1     | 赤红基础（伤害 + 等量魔法 + 赤红伤害成长）  |
| 2 | 5   | 赤红 | **2** | **赤红连续 ✓**（额外一次伤害 + 1 力量） |
| 3 | 4   | 亮黄 | 1     | 亮黄基础（下一张 −1 费 + 1 层下回合能量） |
| 4 | 3   | 亮黄 | **2** | **亮黄连续 ✓**（立刻 +1 能量）      |
| 5 | 2   | 浅橙 | 1     | 浅橙基础（4 格挡）                |
| 6 | 1   | 浅橙 | **2** | **浅橙连续 ✓**（抽 1 张）         |

**每两格同色 + 从新到旧 ⇒ 烧穿满格必然拿到 3 次连续，节奏完全可预期。**  
玩家一眼能数出来"我还能炸几下、炸什么颜色"。

**两条设计含义**：

- **填满不是终点，是起手** —— 填满 6 格 = 攒了一发三连击。
- **赤红在最外层**（最先烧到、最容易烧到）= 快节奏小额；**浅橙在最内层**（要烧穿 5、6 格才够得到）= 慢节奏大额。  
  ⇒ 三色天然形成"**深度越深越值钱**"的梯度，不需要额外的升级链来解释。

### 3.7 「予燎 / 超出格数」的结算规则

> 定稿原话：「**予燎**代表的就是**给予火色**，若给予的火色**超出六格**，**自动触发消耗效果**，超出多少格就触发其原版在格子里面的对应效果（**一次性结算**）」

- 给予时若已满 6 格（只有卡面上面写着的特殊效果的情况下） ⇒ 多出来的格数**立即**按"原格效果"的顺序结算（等价于重新先给再烧）。
- **一次性结算**：不要做成循环 + 每格分别弹 UI；一次算完。
- 例子（来自 `Tomorrowburn`）：超出 1 格 ⇒ 触发 1 次浅橙效果；超出 2 格 ⇒ 2 次浅橙 + 1 次浅橙连续，超出三格 2 次浅橙 + 1 次浅橙连续加一次亮黄。  
  ⚠️ **矛盾点**：这个例子的颜色取法（"超出一格触发一次**浅橙**"）与"从最新格消耗"不符 ——  
  满格时最新格是**赤红**，严格按规则应该是触发**赤红**。⇒ **待裁定**（§七 第 6 项）。

# 紫藤亚里沙（Yalisalin）机制重构 · 设计思路

> 状态：**只写设计，不含代码**。所有结论都基于现有源码 + 原版 STS2 反编译源码（`.local/probe_engine/decomp/`）比对。
> 目标：三套机制（火色 / 余火 / 原罪诅咒）**各自能单独玩，也能混合玩**；同时把复杂度降下来。

---

## 一、现状诊断

### 1.1 三套机制的现状

| 机制 | 触发 | 现状载体 | 是否需要战斗内 UI 操作 |
|---|---|---|---|
| **火色** | 攻击命中给火色；三种颜色可升级；消耗不同颜色换不同额外效果 | **起始遗物** `YalisalinsHairpin`（`RelicRarity.Starter`，**必定拥有，载体本身没问题**） | **要**：`YalisalinFireColorSegmentPicker`（点格子）、`YalisalinSealedColorPicker`（封存色选择）、4 个「封存火焰能力」各自带右键点格子 |
| **余火** | 打出余火牌 → 从手牌/抽牌/弃牌**随机**连一张 → 玩家**选一张**、花能量打出，另一张烧掉；强化 = 强化余火组件 | `YalisalinFireComponentCapability` + `Resolver` | **要**：自定义选牌界面（`YalisalinFireComponentSelectionRegistry` + `ChoiceCommand`）+ 右键「添火」+「跳过添火」按钮 |
| **原罪诅咒** | 回合结束自动保留 → 立刻「宽恕」；打出 → 「自惩」 | `Characters/Common/Components/Originalsin.cs`（**全角色共用组件**） | 否 |

### 1.2 五个根因

~~1. 机制载体错位~~ **（已撤回）**：`YalisalinsHairpin.Rarity = RelicRarity.Starter`，是**起始遗物、必定拥有**，
所以"没拿到发夹 ⇒ 火色废掉"不成立；用起始遗物承载角色机制本身就是原版做法（Defect 的 `Cracked Core`）。
**火色的真问题不是"挂在哪"，是"有多少个维度"** —— 见下面的 1'。

**1'. 火色的状态维度太多（"太复杂"的第一来源）**
`YalisalinsHairpin.cs` **1576 行**，对外暴露的火色操作有：加（`TryAddFireColor`）、升级（`TryConvert`）、
强升（`TryStrongConvert`）、降级（`TryDowngrade`）、末段前移（`TryMoveLastToFront`）、消耗（`ConsumeFireColor`）、
封存/取封存/复制封存（`TrySealEarliest` / `TrySealSegment` / `TryUseSealed` / `TryCopySealed`），
外加**每种颜色各一套配对进度**（`RedConsumePairProgress` / `OrangeConsumePairProgress` / `YellowConsumePairProgress`）、
「本回合上次消耗的颜色」、以及**分颜色写的三套消耗奖励**（`ResolveSingleFireColorConsumedReward` / `...RedFireColor...`）。

玩家实际要同时记住：敌人身上挂了几段什么颜色、**顺序**（因为有"最早/最高/末段前移"）、三种颜色各自**消耗后给什么**、
三种颜色的**配对进度**到几了、封存区里存了什么、以及 4 个封存能力各自的右键操作。
⇒ 这是原版任一角色记忆负担的数倍。原版 Defect 的球是：3 种球 × 每种 1 个效果，全部写在卡面上、且球可见。
**砍法：只留「加 / 消耗」两个动作 + 「颜色」一个属性，其余维度全砍。**

2. **火色和余火都要玩家在战斗里点 UI**
   原版 STS2 **没有任何角色**需要玩家在战斗中点格子 / 右键菜单 / 自定义选牌界面。所有原版机制都能写成「卡面文本 + 层数/标记」。
   这是"太复杂"的第一来源。

3. **余火每次打出都要一次决策**
   `Resolver.cs` 524 行 + `SelectionRegistry.cs` 269 行 + `ChoiceCommand.cs` 139 行 + 两个 Picker 251 行 ≈ **1200 行交互代码**。
   每张余火牌打出 = 玩家要看 2 张牌 → 算能量 → 决定要不要右键添火 → 确认。认知负担随出牌数**线性增长**。
   对照原版：Defect 的 `Dualcast` / `Recursion` 是"确定性 + 零 UI"。

4. **三套机制里只有火色自带"发动机"，另外两套没有 —— 这才是"体系卡强绑定"的根因**
   - 火色：**攻击就产** ⇒ 每回合自动有资源，自成闭环。
   - 余火：不产任何资源，只**消耗**（能量 + 一张牌）⇒ 必须靠牌库和能量供养。
   - 原罪诅咒：本身是**负债**（占手牌的诅咒），只有宽恕/自惩那一刻才有产出。
   ⇒ 于是三套只能各玩各的：余火卡拿不到火色的好处，诅咒卡也拿不到，谁都不欠谁 ⇒ **混玩没有任何接口，必然稀释**。
   没有任何一张卡同时引用两套机制 —— 这就是"体系卡强绑定"的本质：不是为了强度而绑，是因为不绑就完全没用。

5. **卡池结构失衡（91 张的分布）**

   | 类别 | 数量（约） | 备注 |
   |---|---|---|
   | 火色/火体系 | ~16 | `YalisalinFireComponentCards.cs` 一个文件里塞了 16 张 |
   | 原罪诅咒 | ~25 | 而且是**全角色共用**的东西，塞在亚里沙池里占比过高 |
   | 其它角色的羁绊/魔法卡 | ~11 | `YalisalinAam/Amm/Kkm/Lym/Mgm/Mllm/Mlym/Nym/Nyxm/CardTen/Twelve` |
   | 基础攻防 | ~10 | 打击/防御/魔女之力/魔女囚犯/魔女审判/书本中的真相… |
   | 杂项（看不出归属） | ~19 | Grazingcritical / Unusedconclusion / SelfDestruct2887 / Thirteenthlistener … |

   ⇒ 真正服务"亚里沙三体系"的卡只有一半左右。

### 1.3 附带的技术债

- 亚里沙自己的卡**没有** `YALISALIN_` 本地化前缀（`Ignite` / `ExtinguishFlame` / `SinMarket` 等都占着通用命名空间），反而是**别的角色**的卡挂了 `YALISALIN_` 前缀 ⇒ 检索和定位都很痛苦。
- `ExtinguishFlame` / `LinkTheFire` / `UsurpTheFlame` 注册在 `LinCardPool`（通用池），不在亚里沙池 ⇒ 亚里沙自己抽不到自己的火卡。
- 余火走自定义联机命令（`YalisalinFireComponentChoiceCommand` 打包索引 + 右键记录），是 desync 高风险区。

## 二、原版 STS2 与本项目参照

### 2.1 原版角色怎么处理"多机制"

| 角色 | 结构 | 关键手法 |
|---|---|---|
| **Defect** | 单主轴（充能球）+ 卡分三类：生成球 / 触发球 / 利用球 | 纯冰 / 纯电 / 纯暗都能单独成立；混玩靠 `Focus`（集中）**统一加成** ⇒ 混玩是加乘而非稀释 |
| **Silent** | 三轴：毒 / 闪避 / 弃牌 | "**弃牌**"是通用动作：弃牌卡既能喂毒也能喂闪避 ⇒ 有一根横贯的梁 |
| **Ironclad** | 自伤 + 力量 + 消耗 | "**自伤**"是统一货币：所有轴都往"掉血"兑换 |
| **Regent** | 站位（Alignment）+ 星辰/光 | 光是统一资源，站位决定光的兑换率 |

**核心规律：原版每个角色都有"一个统一货币 + N 个花费通道"，或者"一个主轴 + N 个副轴都往主轴兑换"。**
亚里沙现在**缺的就是那个统一货币** —— 火色、余火、诅咒三条各赚各的、各花各的。

### 2.2 本项目内部参照：艾玛的【审判】

艾玛也有"三种东西"（赞同 / 反驳 / 疑问附魔），做法是：
- 三种**统一成一个概念**【审判】，卡面只写【审判】不写具体是哪一种；
- 计数统一走 `EmalinCombatHelper`：数「**种**」用 `GetDistinctEnchantmentTypesThisTurn`，数「**张**」用 `GetTotalEnchantmentPlaysThisTurn`；**卡面写"N种"就必须用 distinct 那个**；
- 同样的框架下，纯单附魔（只打赞同）和三种混打都能成立。

⇒ 亚里沙的"三种火色"完全可以照这个思路：**对外统一叫【火色】，颜色只是内部段位**，卡面绝大多数时候只写「消耗 N 段火色」，只有少数卡点名"赤红段"。

## 三、重构目标（可验收）

1. **单轴闭环**：只打火色卡 / 只打余火卡 / 只打诅咒卡，各自都能打完一层（含基础攻防支撑）。
2. **混轴有正收益**：存在明确的跨轴卡与兑换关系，混玩 ≥ 单玩。
3. **战斗内零额外 UI**：所有机制都能写成卡面文本 + 层数；删掉点格子、右键菜单、封存区。
   （起始遗物是必定拥有的，所以机制挂在起始遗物上完全 OK —— 原版 Defect 的 `Cracked Core` 就是这么做的，
   这条**不是**问题，不用改。）
5. **卡池 ~80 张**，其中 ≥15 张明确跨轴。

## 四、主推方案 A：一个货币 + 三个通道

> 一句话：**火色 = 唯一的货币；余火 = 花货币的"立即通道"；原罪诅咒 = 花货币的"延时/存储通道"。**

### A1 · 火色：载体不动（发夹是对的），**只砍维度 + 砍 UI**

载体保持 `YalisalinsHairpin`（起始遗物，必定拥有，正统做法）。要动的是"它上面挂了多少东西"：

**保留（这是这套机制的灵魂，不动）**
- 「**只要攻击就给火色**」—— 唯一的生产方式，清爽、好懂、有 feedback。
- 「**三种颜色、消耗不同颜色换不同效果**」—— 这是风味与构筑差异的来源，保留。

**砍掉的维度（每条都对应上面诊断里的"玩家记不住"）**

| 砍掉 | 现在 | 为什么砍 |
|---|---|---|
| 封存 / 取封存 / 复制封存（`TrySealEarliest` / `TrySealSegment` / `TryUseSealed` / `TryCopySealed`）+ 4 个「封存火焰能力」 | 4 个能力 + 一整套封存区 | 一层玩家看不见的隐藏库存；且这四个能力各自带右键点格子 |
| 降级 `TryDowngradeFireColor` | 1 个操作 | 与"升级"语义相反，玩家不知道什么时候该用 |
| 末段前移 `TryMoveLastToFront` | 1 个操作 | 只有记住队列顺序才用得上，是纯隐藏状态 |
| 强升 `TryStrongConvert` | 1 个操作 | 与 `TryConvert` 重叠 |
| 三种颜色各自的「配对进度」计数 | 3 个 `[SavedProperty]` | 玩家看不见，只在结算时才体现 ⇒ 全部改成"消耗即得" |
| 分颜色写的三套消耗奖励方法 | 3 套 | 收敛成一张表（颜色 → 效果），数据驱动 |

**砍掉的 UI**
- `YalisalinFireColorSegmentPicker`（点格子）、`YalisalinSealedColorPicker`（封存色选择）→ 全删。
- 消耗改为**自动**：卡面写「消耗 N 段火色：…」/「消耗全部火色，每段 X」，结算时自动扣，**不弹任何界面**。
- 升级改为**自动或卡面指定**：累计 N 段自动升，或写「把你的一段火色升级」（一次性，不点格子）。

**目标形态**：火色 = 「一段段挂在敌人身上的彩色标记」，玩家只需要知道 **我有几段、是什么颜色**；
操作只剩 **加** 和 **耗** 两个，且都写在卡面上。发夹代码 1576 行 → 目标 **< 400 行**。

### A2 · 余火：**连接保留随机**（已定），只砍决策层数

> **保留随机**是既定选择 —— 随机带来的赌博感是这套机制的乐趣，不能动。
> 那么复杂度只能从"决策层数"上砍：现在每张余火牌打出 = **两次决策**（选哪张 + 要不要右键添火/跳过）。

- **砍掉第二层决策**：删除右键「添火」、删除「跳过本次添火」按钮、删除自定义选牌界面里的右键分支
  （`YalisalinFireComponentSelectionRegistry.TryHandleRightClick` / `OnSkipStrengthenPressed` / 两个 Picker）。
  ⇒ 每次打出只剩「选一张」这**一次**决策，和原版任何一张"选一张牌"的卡认知成本一致。
- **"添火"改写成卡面费用**，而不是隐藏的右键：
  「**额外消耗 1 段火色**：连到的牌免费打出 / 连两张 / 连到的牌升级后打出」。
- **⚠️ 火色对余火必须是"可选加成"，不能是"必需燃料"**：
  「连到的牌可以打出」这件事**不消耗火色也要成立**，否则单玩余火就不闭环（余火牌自己不产火色）。
  火色只负责让它**更强**（免费 / 多连 / 升级）。
- **强化 = 强化余火组件**保留（这是好设计，直观且省卡位）。
- 预计可删 ~600–800 行（两个 Picker + 右键/跳过分支 + ChoiceCommand 里打包右键记录的那一段）。

> 若还想再降一档（备选 A2-2）：连到的牌**自动打出**、零决策，余火牌变成"打出时附带打出一张随机牌"。
> 这个更干净，但会丢掉"选一张"的策略感，所以**不推荐**，只作为如果你觉得还是太吵时的退路。

### A3 · 原罪诅咒：从「独立体系」改成「火色的存取通道」

- **保留（宽恕）→ 产火色**：例如「宽恕时获得 2 段火色」，或更有味道的「把当前火色**存进**这张诅咒卡」。
- **打出（自惩）→ 大量消耗火色换爆发**：例如「消耗全部火色，每段造成 X 伤害 / 抽 1 张牌」。
- **纯诅咒闭环成立**：宽恕自己产火色 → 诅咒自己的卡自己消耗 ⇒ 自成循环 ✓
- **混玩有收益**：诅咒产的火色能给火色卡和余火卡用 ⇒ 兑换 ✓
- 诅咒卡从 25 张瘦到 ~15 张，只留能产/耗火色的；其余回到 `LinCardPool`（本来就是全角色共用的东西）。

### A4 · 跨轴卡规则（治"强绑定"）

**硬规则：亚里沙卡池里每张卡至少挂两个标签**（火色 / 余火 / 诅咒 中取两个，或"通用 + 一轴"）。模板：

- 攻击牌：造成伤害 + 给 1 段火色 + 「若你手上有原罪诅咒，额外 X」（火 × 诅咒）
- 技能牌：获得格挡 + 「若本回合打出过余火牌，额外 Y」（余火 × 通用）
- 能力牌：回合开始给火色 / 打出余火牌时触发（火 × 余火）
- 基础打击/防御**也要产火色** ⇒ 保证"只打火色"有基础支撑

### A5 · 卡池重排（91 → ~80）

| 类别 | 现在 | 目标 | 处理 |
|---|---|---|---|
| 火色主干（含 10 张基础攻防） | ~10 | ~30 | 基础攻防全部改为能产火色；新增纯火色卡 |
| 余火 | ~16 | ~20 | 全部带「消耗火色」字样 |
| 原罪诅咒 | ~25 | ~15 | 只留能产/耗火色的，其余回 `LinCardPool` |
| 跨轴/通用 | ~0 | ~15 | **新增**，专门奖励混搭 |
| 其它角色羁绊卡 | ~11 | 0 | 迁到通用池或删除（待你拍板） |
| 杂项 | ~19 | 0 | 重新归类或删除 |

## 五、备选方案

### 方案 B：三轴并列 + 引入统一代币「灰烬 Ash」（改动最小地解决"混玩没收益"）

- 三套机制都产出 / 消耗「灰烬」；火色决定灰烬能换什么（颜色 = 兑换表）；余火 = 立即花灰烬；诅咒 = 延时存灰烬。
- 优点：三套机制的内部逻辑基本不动，只加一层货币。
- 缺点：**又多一个概念**（可能反而更"复杂"），且不解决 UI 复杂度、不解决载体错位。

### 方案 C：只加跨轴奖励卡（最小改动）

- 新增 12 张跨轴卡（每对轴 4 张）。
- 优点：最快见效。
- 缺点：**完全不解决"太复杂"**，也不解决"没拿到发夹 = 火色废掉"。

**推荐 A**。若想渐进：先做 A1 + A3（去载体依赖 + 去 UI + 诅咒联动），A2 放最后（动余火是最大的一块）。

## 六、分阶段实施与验收

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **1** | 火色砍维度（删封存/降级/末段前移/强升/配对进度）+ 删两个 Picker + 删 4 个封存能力的右键 | 战斗中无任何点格子/右键；发夹文件 < 400 行；火色的操作只剩"加/耗" |
| **2** | 诅咒宽恕产火色、自惩耗火色；诅咒瘦身到 ~15 张 | 只带诅咒 + 基础攻防能打完一层 Boss |
| **3** | 余火删右键添火 + 跳过按钮 + 自定义选牌界面（连接**保持随机**、保留"选一张"）；火色做成可选加成 | 只带余火卡能打完一层；余火交互代码 < 300 行 |
| **4** | 卡池重排 + 新增 ~15 张跨轴卡 | 每套单轴各自能通关；双轴/三轴有明确 combo |
| **5** | 数值调整 + 本地化键统一（亚里沙卡加 `YALISALIN_` 前缀） | 三套混玩 ≈ 或 > 任一单轴 |

## 七、需要你先拍板的 3 件事

1. **火色的"升级"链要不要留？**
   - 留（赤红 → 浅橙 → 亮黄 逐级升）⇒ 有成长感，但多一维；
   - 砍成"三种颜色各自独立、不互转" ⇒ 最省脑子，代价是少一条成长线。
   （我倾向**留升级、但改成自动/卡面指定**，因为它就是"不断提升"这个你想要的爽点。）
2. **余火的「选一张」要不要也删掉（退到 A2-2 自动打出）？**
   我倾向**保留选一张**（只砍右键/跳过），因为它还背着策略感；但如果你觉得还是吵，A2-2 是退路。
3. **11 张别的角色的羁绊卡**（夏目安安 / 樱羽艾玛 / 二阶堂希罗 …）：删掉，还是迁到通用池让所有角色都能拿到？

> 已定：**余火连接保留随机**（不改成确定性）、**火色继续挂在发夹上**（不改成角色能力）。
